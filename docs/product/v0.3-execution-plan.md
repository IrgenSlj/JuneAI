# June v0.3 — Execution Plan

**Created:** 2026-07-25. **Status:** Active sequencing doc.

`v0.3-development-plan.md` says *what* and *why*. This says *in what order, in what
slices, and how we know each one is done*. Where the two disagree on sequencing,
this wins; where they disagree on intent, that one wins.

Every slice below is: one branch of work → `./tools/check.sh` green → one commit →
push. No batching. Slices are sized so that no single one takes more than a day.

---

## Ordering rationale

Three constraints drive the order.

1. **Nothing public is currently usable.** The only downloadable artifact is a
   2.7MB shell with no brain inside it. Until that is fixed, every hour spent on
   the front page markets a broken download. Distribution correctness comes first.
2. **You cannot demo what you cannot install.** The GIF, the diagrams, and the
   README rebuild all depend on the app running end-to-end from a cold install.
   That dependency forces the release work ahead of the visual work.
3. **Unmeasured features are liabilities.** Four-signal retrieval fusion shipped
   without a benchmark proving it beat vector-only. That number is both an
   engineering gate and the strongest sentence on the future front page — it must
   exist before the front page is written.

So: **truth → working artifact → proof → visual identity → front page → depth**.
Phases 1-5 are roughly three weeks and end with a repo and a download a stranger
can trust. Phases 6-11 are the product depth that turns a trustworthy download
into a product people keep.

## Phase 2 — Prove the retrieval work (2-3 days)

Four-signal fusion (vector + BM25 + entity + temporal, RRF `k=60`) shipped in
`15c14ab6` with unit tests but no measurement against the vector-only baseline.
Until that number exists, the biggest feature of v0.3 is unverified — and it is
also the single most persuasive fact for the front page.

| Slice | Work | Acceptance |
|---|---|---|
| **2.1** | Build the golden corpus: 100 query/expected-fact cases across the real recall shapes (name recall, temporal supersession, entity-linked, paraphrase, negation, multi-hop) | Fixture committed; generation script reproducible |
| **2.2** | Benchmark harness measuring recall@8, MRR, and p95 latency for vector-only vs. full fusion, with per-channel ablation | `pytest` marker runs it; results table emitted as markdown |
| **2.3** | Tune `RetrievalConfig` weights against the corpus; document the chosen defaults and why | ≥10% recall@8 improvement over vector-only; p95 <120ms on a 50k-fact corpus |
| **2.4** | Wire the benchmark into `check.sh` as a non-blocking report (blocking would make the gate slow and flaky) | Gate stays fast; regressions visible |

If 2.3 fails to clear +10%, that is a finding, not a failure — it means the fusion
weights or the entity/temporal channels need work, and we would rather know now
than after publishing the claim.

## Phase 6 — Promise checkpoint/resume (3-4 days)

The largest gap between a headline claim and the code. Inversion #2 is "continues,
not completes," but resume re-runs the goal from scratch. Fixing this is what makes
the claim honest.

| Slice | Work | Acceptance |
|---|---|---|
| **6.1** | ADR: checkpoint model — what a step is, what is durable, what replay guarantees hold | ADR 0025 accepted |
| **6.2** | Per-step durable state in `tasks/`, migration included | Schema versioned; rollback path documented |
| **6.3** | Resume from last completed step, with replay-safety for non-idempotent steps | Kill mid-promise → resume → no repeated side effects |
| **6.4** | UI: show checkpoint position in the trace | Visible in `/tasks` |

## Phase 8 — June as infrastructure (2-3 days)

Expose June's memory as an MCP server so ChatGPT, Claude, and other assistants can
read it. Users run 4.2 assistants on average; being the memory layer *for* them is
a stronger position than competing with all of them.

| Slice | Work | Acceptance |
|---|---|---|
| **8.1** | ADR: what June exposes, what it never exposes, how consent is expressed | ADR accepted |
| **8.2** | MCP server over the `MemoryManager` facade — read + search first, no writes | Works from a third-party MCP client |
| **8.3** | Per-tool consent surfaced in the UI and ledgered | Every external read appears in Receipts |

## Phase 9 — Integrations (5+ days)

Calendar first (`skills/calendar` exists as a stub), then email. This is the line
between "chatbot" and "assistant": surfacing action items and prepping meetings
requires June to see the user's actual week.

## Phase 10 — Voice I/O (5+ days)

Local Whisper for STT, Piper/Coqui for TTS, cloud fallback only on consent. Table
stakes by 2027 per the market read, but deliberately after the trust and
distribution work — a voice interface on an uninstallable app helps no one.

## Phase 11 — Memory governance depth (large)

ADR 0026 (Night Shift vs. no-heartbeat reconciliation), memory provenance +
quarantine columns, the injection heuristic in `guard/injection.py`. Each needs its
ADR before implementation; each touches the privacy boundary and must document it.

---

## Continuous, not phased

- Accessibility pass (ARIA, keyboard nav, screen reader) — a slice per phase, not a
  sprint at the end.
- Playwright coverage extended as each new surface ships.
- Every privacy-boundary change documented in the same commit.
- `./tools/check.sh` green before every push, always read directly, never through a
  pipe.
