## Why the order changed

The original plan optimised product quality and presentation, and assumed
distribution would follow. The numbers say otherwise: **835 commits over 16
months, 0 stars, 0 forks, 0 downloads, 2 watchers.** Phases 0-3 made a good
product demonstrably better and considerably more presentable. None of them put
June in front of a human being, and Phase 5 as originally written ("rebuild the
front page") improves a page nobody visits.

Two facts from the review reset the strategy:

1. **The local-first-open-source-assistant race has a winner, and it is not
   June.** OpenClaw reached ~353K GitHub stars, 3.2M active users and 500K
   running instances in under five months, occupying exactly the position this
   plan called "a defensible wedge nobody else combines." Competing on
   *local-first* is competing on the incumbent's strength.
2. **That incumbent has a structural weakness June already answers.** In
   February 2026 SecurityScorecard observed 40,214 internet-exposed OpenClaw
   instances with 35.4% flagged vulnerable; the CVE list includes
   prompt-injection-driven code execution and a CVSS 8.8 cookie exfiltration via
   a rendered link preview. June is loopback-only, gates every tool call through
   one guard seam, tracks taint across calls, and writes a hash-chained record of
   everything. That is the differentiator, and it is already built and tested.

So the axis moves from **"local-first personal AI"** to **"the agent that can
prove what it did"** — and the first job is no longer polish, it is *reach*.

## Phase 4 — June as infrastructure (MCP server) · 3-4 days

**The trial funnel the plan never had.** Today the only way to meet June is to
own an Apple Silicon Mac, install Ollama, and download ~8GB. An MCP server lets
someone already running Claude Desktop, Cursor or OpenClaw use June's memory and
receipts in minutes, on any platform, with no model download.

| Slice | Work | Acceptance |
|---|---|---|
| **4.1** | ADR: what June exposes over MCP, what she never exposes, how consent is expressed and revoked | ADR accepted before code |
| **4.2** | MCP server over the `MemoryManager` facade — **read and search only**, no writes in v1 | Works from a third-party MCP client end to end |
| **4.3** | Every external read surfaced in the UI and written to the ledger as its own kind | A session from Claude Desktop is fully reconstructable from Receipts |
| **4.4** | Per-tool consent with revocation, defaulting to denied | Nothing is readable until explicitly granted |
| **4.5** | Quickstart in the README: connect June to Claude Desktop in under five minutes | A stranger completes it without reading source |

**Why read-only first:** a memory server that can be *written* by any connected
agent is a poisoning vector, and June's whole claim is that she can prove where a
memory came from. Writes wait for provenance columns (Phase 6).

## Original ordering rationale (2026-07-25, superseded)

Kept for provenance. Three constraints drove the original order.

1. **Nothing public is currently usable.** The only downloadable artifact is a
   2.7MB shell with no brain inside it. Until that is fixed, every hour spent on
   the front page markets a broken download. Distribution correctness comes first.
2. **You cannot demo what you cannot install.** The GIF, the diagrams, and the
   README rebuild all depend on the app running end-to-end from a cold install.
   That dependency forces the release work ahead of the visual work.
3. **Unmeasured features are liabilities.** Four-signal retrieval fusion shipped
   without a benchmark proving it beat vector-only. That number is both an
   engineering gate and the strongest sentence on the future front page — it must
   exist before the front page is written.

That reasoning held for Phases 0-3 and produced them. It broke at Phase 4,
because every remaining step assumed an audience that the traction numbers say
does not exist.

## Phase 1 — A download that works (2-3 days)

**The headline defect.** `v0.1.0`'s published asset was cut 2026-05-25; the
PyInstaller sidecar pipeline landed 2026-07-01. The shipped `June.app` contains
only `June.icns` under `Resources/` — no `june-api/`. Local builds are correct
(43MB DMG, sidecar staged), so this is release hygiene, not engineering.

| Slice | Work | Acceptance |
|---|---|---|
| **1.1** | Build a release DMG from current `main` via `tools/packaging/build-sidecar.sh` + `tauri build`; verify `Contents/Resources/june-api/june-api` exists and the bundle is ~43MB | `hdiutil attach` on the built DMG shows the sidecar binary |
| **1.2** | **Cold-install verification.** Install from the DMG on a machine state that has never run the repo: no `.venv`, no repo checkout, fresh data dir. Walk first-run: Gatekeeper bypass → Ollama detection → model pull → provider verify round-trip → first message → memory write → provenance frame | A written cold-start log with every failure found; all blocking failures fixed |
| **1.3** | Fix whatever 1.2 surfaces (expect: Ollama bootstrap UX, first-run copy, missing-model messaging, sidecar startup timing) | Cold install works unattended by someone who has never seen the repo |
| **1.4** | Sidecar health poll backoff — currently 500ms x 120 (60s worst case), should be exponential from the first poll | Startup feels instant when the sidecar is fast; no regression when slow |
| **1.5** | Re-cut `v0.1.0`: move the tag to current `main`, delete the stale asset, upload the working DMG, rewrite the release notes for what actually ships today | `gh release view v0.1.0` lists a ~43MB asset; notes describe current `main` |
| **1.6** | README install section: real download link, Gatekeeper first-launch instructions, Ollama + model-pull prerequisites with disk-space numbers (`gemma4:e2b` is 7.2GB — say so) | A stranger can go from README to working app without reading source |

**Explicit non-goal:** notarization. It stays blocked on Apple Developer
enrollment `[FOUNDER]`. Ad-hoc signing plus honest Gatekeeper instructions is the
correct alpha posture.

**Phase 1 outcome (2026-07-25).** All six slices landed. The walk found a
release-blocking hang (macOS Keychain, packaged builds only —
[log](cold-install-log-2026-07-25.md)), fixed in `ec7d92ec`. `v0.1.0` now carries
a verified 45MB DMG built by CI from the tag, and the tag points at the code it
was built from.

**Open `[FOUNDER]` item — release automation.** The release workflow builds
correctly but cannot publish: `Create GitHub Release` fails with *Resource not
accessible by integration* because the repository caps the workflow token at
read-only (`default_workflow_permissions: read`). The v0.1.0 asset was therefore
downloaded from the CI run and uploaded by hand. To make tag pushes publish on
their own, flip Settings → Actions → General → Workflow permissions to **Read and
write**, or equivalently:

```sh
gh api -X PUT repos/IrgenSlj/JuneAI/actions/permissions/workflow \
  -f default_workflow_permissions=write
```

This is a repository-wide permission change, so it is the founder's call rather
than something to apply silently. Until it is made, every release needs the
manual download-and-upload step.

## Phase 2 — Prove the retrieval work (2-3 days)

Four-signal fusion (vector + BM25 + entity + temporal, RRF `k=60`) shipped in
`15c14ab6` with unit tests but no measurement against the vector-only baseline.
Until that number exists, the biggest feature of v0.3 is unverified — and it is
also the single most persuasive fact for the front page.

| Slice | Work | Acceptance |
|---|---|---|
| **2.1** | Build the golden corpus: 100 query/expected-fact cases across the real recall shapes (name recall, temporal supersession, entity-linked, paraphrase, negation, multi-hop) | Fixture committed; generation script reproducible |
| **2.2** | Benchmark harness measuring recall@8, MRR, and p95 latency for vector-only vs. full fusion, with per-channel ablation | `pytest` marker runs it; results table emitted as markdown |
| **2.3** | Tune `RetrievalConfig` weights against the corpus; document the chosen defaults and why | ≥10% recall@8 improvement over vector-only; p95 <120ms on a 50k-fact corpus |
| **2.4** | Wire the benchmark into `check.sh` as a non-blocking report (blocking would make the gate slow and flaky) | Gate stays fast; regressions visible |

If 2.3 fails to clear +10%, that is a finding, not a failure — it means the fusion
weights or the entity/temporal channels need work, and we would rather know now
than after publishing the claim.

## Original Phases 4-11 (superseded 2026-07-26)

The original sequence after Phase 3 was: demo GIF, rebuild the front page,
promise checkpoint/resume, update mechanism, MCP server, integrations, voice,
memory governance depth. Every item survives in the re-ordered plan above except
that their order changed and two were deferred outright (voice, Night Shift).

The substantive change: the MCP server moved from ninth to first, because it is
the only item that puts June in front of someone without an Apple Silicon Mac
and an 8GB download; and a launch phase was added, because the original plan had
none. Full detail is in git history for this file.
