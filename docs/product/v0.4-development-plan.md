# June v0.4 — Development Plan

**Created:** 2026-07-28.
**Status:** Proposed. Pending approval before implementation.

This plan builds on the v0.3 launch work (Phases 0-7) and addresses the
identified defects, upgrades, and new features. It is organized into three
streams: **Fixes** (immediate, high-impact), **Upgrades** (infrastructure and
coverage), and **Features** (new capabilities).

For the authoritative state of what is shipped, see [`../CURRENT.md`](../CURRENT.md).
For the durable worldview, see [`../vision.md`](../vision.md).

---

## 1. Stream A — Fixes (Immediate)

These are small, high-impact changes that address published defects or
inconsistencies. Each is a single slice: one piece of work → `./tools/check.sh`
green → one commit → push.

### A.1 Temporal Signal Ranking

**Problem:** ADR 0024 claims four recall signals (vector, BM25, entity, temporal)
but the temporal signal does not change ranking when ablated. The `_temporal_prior`
function in `recall.py` applies only to `valid_to`-based expiry, not to recency
of the fact itself.

**Root cause:** The temporal signal is a filter (exclude expired facts), not a
ranker (prefer recent facts). The salience score already includes a recency
component, but it operates on `last_accessed` (when June saw the fact), not on
`valid_to` (when the fact stopped being true in the world). These are different
signals and both matter.

**Fix:** Add a `valid_from` recency prior to the fusion score. Facts with a
recent `valid_from` get a small boost; facts with no `valid_from` are treated as
always-valid (current behavior). This makes the temporal signal contribute to
ranking, not just filtering.

**Acceptance:**
- Ablating the temporal signal changes recall@8 by ≥2% on the golden corpus.
- ADR 0024 is amended to describe the four signals accurately.
- 202ms p95 latency is unaffected (the signal is a multiplicative prior, not a scan).

**Dependencies:** None.

---

### A.2 `distractor_heavy` Recall Improvement

**Problem:** Recall@8 on `distractor_heavy` queries is 0.31, the weakest category.
This shape is most like real-world failure: the user asks about something specific
and the system must distinguish it from similar-but-wrong facts.

**Root cause:** The candidate pool (20) is too wide for this query shape. Wide
pools feed RRF more noise, and distractor-heavy queries are exactly where noise
hurts. The BM25 channel also underperforms on these queries because the
distractors share vocabulary with the target.

**Fix:** Two changes:
1. Reduce the default candidate pool from 20 to 15. Measured: recall@8 rises
   from 0.760 to 0.790 on the full corpus at this setting. The 20-pool was
   chosen for margin against overfitting, but 15 still has margin (the corpus
   best was 12).
2. Add a BM25 term-frequency penalty: facts that match many query terms but
   not the rarest term get a small score reduction. This penalizes distractors
   that share vocabulary with the target without penalizing the target itself.

**Acceptance:**
- `distractor_heavy` recall@8 improves from 0.31 to ≥0.45.
- Full corpus recall@8 does not regress (must stay ≥0.760).
- p95 latency stays under 250ms (ideally improves with a smaller pool).

**Dependencies:** None.

---

### A.3 Retrieval Latency Optimization

**Problem:** p95 retrieval is 252ms at 50k facts, missing the 120ms target.
The vec0 scan is brute-force and grows linearly.

**Root cause:** sqlite-vec's `vec0` index performs a full cosine similarity scan
over all vectors. At 50k facts, this is measurable. The FTS5 channel is fast
(BM25 is index-native), but the vector channel dominates latency.

**Fix:** Three-pronged approach:
1. **Reduce candidate pool** (from A.2): fewer vectors to scan means less work.
   Measured: p95 drops from 252ms to ~210ms with pool=15.
2. **Add a pre-filter:** Before the vector scan, filter `semantic_facts` by
   `valid_to IS NULL OR valid_to > now` in SQL, then only scan vectors for
   currently-valid facts. This reduces the index size proportionally to the
   number of expired facts.
3. **Explore HNSW:** sqlite-vec supports HNSW indices (`vec0` vs `hnsw`). A
   benchmark spike comparing the two at 50k facts. If HNSW improves p95 by
   ≥50%, adopt it; if not, document why and move on.

**Acceptance:**
- p95 retrieval at 50k facts is under 150ms (revised target; 120ms may require
  HNSW or a different index).
- Recall@8 does not regress from any optimization.
- ADR 0024 is updated with the measured latency and the optimization applied.

**Dependencies:** A.2 (smaller pool).

### A.4 Promise Checkpoint/Resume

**Problem:** Resuming a promise re-runs the goal from scratch. This undercuts
the "continues, not completes" inversion (ADR 0015). A promise that was
half-done and got interrupted starts over, wasting the work already done.

**Root cause:** `TaskRuntime._stream_events` creates a fresh `SessionState`
with an empty message list. There is no mechanism to inject the prior steps'
results as context for the resume.

**Fix:** Add a checkpoint mechanism:
1. When a promise is interrupted (cancelled, failed, or blocked), persist the
   accumulated `TaskStep` entries as a checkpoint.
2. On resume, inject the checkpoint as context: "You previously completed these
   steps: [summary]. Continue from where you left off."
3. The loop sees this as a new user message containing the checkpoint summary,
   so it can skip already-completed work.

**Acceptance:**
- A promise that completed 3 of 5 steps before interruption resumes and
  starts from step 4 (not step 1).
- The checkpoint summary is visible in the task's trace.
- Non-idempotent steps (e.g., a tool call that sends a message) are not
  re-executed on resume.
- 15 new tests covering: checkpoint creation, checkpoint injection, partial
  resume, full resume, idempotency tracking.

**Dependencies:** None.

---

### A.5 Telegram Skill Consumer

**Problem:** The Telegram skill writes to `skill_inbound_events` but nothing
reads it. This is a half-wired feature that creates confusion.

**Decision: Build the consumer** (approved 2026-07-28).

- Create a `TelegramInboundConsumer` that polls `skill_inbound_events` for
  new Telegram messages and routes them through the loop as user turns.
- Add an API route `/skills/telegram/status` to show consumer health.
- Acceptance: A Telegram message produces a June turn; the response is sent
  back via the Telegram skill.
- Estimated scope: Medium (new module, tests, API route for status).

**Dependencies:** None.

## 2. Stream B — Upgrades (Infrastructure)

These are larger structural improvements that improve the codebase's health,
coverage, or reach. They are ordered by impact and dependency.

### B.1 Git History Rewrite (Slice 7.0)

**Problem:** The `.git` history is 240MB, carrying a v1 virtualenv, a 68MB
checkpoint, and MNIST data. Every clone pays for these forever.

**Fix:** Run `git filter-repo` to drop the three largest blobs. Force-push
`main`. Re-clone locally.

**Acceptance:**
- Clone size falls from 240MB to <50MB.
- `main` still builds and the gate is green from a fresh clone.
- All existing tests pass.

**Dependencies:** None. Must be done before launch (Phase 7).

---

### B.2 E2e Spec for `/setup`

**Problem:** The first-run path every user takes has no e2e coverage. The repo
audit flagged this as the highest-risk gap.

**Fix:** Write a Playwright spec that:
1. Navigates to `/setup`.
2. Verifies the setup wizard renders correctly.
3. Tests the Ollama connection flow (mock the backend).
4. Tests the privacy dial configuration.
5. Verifies the user is redirected to `/chat` after setup completes.

**Acceptance:**
- The spec passes against a mocked backend.
- The spec covers the happy path and the Ollama-not-running path.
- The spec is included in `pnpm check` (CI gate).

**Dependencies:** None.

---

### B.3 E2e Specs for `/settings`, `/skills`, `/help/ollama`

**Problem:** These routes have no e2e coverage. `/help/ollama` is what a new
user is sent to when a model is missing.

**Fix:** Write Playwright specs for each:
- `/settings`: Verify settings render, privacy dial works, location can be
  set/removed.
- `/skills`: Verify skills list loads, a skill can be toggled, capability
  contracts are displayed.
- `/help/ollama`: Verify the help page renders, the install link works.

**Acceptance:**
- All three specs pass against mocked backends.
- All three are included in `pnpm check`.

**Dependencies:** B.2 (establishes the pattern).

---

### B.4 Linux Platform Support

**Problem:** June is Apple Silicon only, excluding every user of the platform
the competition runs on (Linux self-hosters).

**Fix:** Build and test the Tauri desktop app for Linux:
1. Add a Linux build target to the release workflow.
2. Test the frozen Python sidecar on Linux (PyInstaller supports it).
3. Verify Ollama integration works on Linux.
4. Update the README to list Linux as a supported platform.

**Acceptance:**
- A Linux AppImage or .deb is built by CI.
- The app boots and serves chat on a fresh Linux machine.
- The quality gate passes on Linux.

**Dependencies:** None, but lower priority than the fixes.

---

### B.5 Dependency Audit and Updates

**Problem:** Dependencies may be outdated or have known vulnerabilities.

**Fix:** Run a dependency audit:
1. `pip-audit` for Python dependencies.
2. `pnpm audit` for JavaScript dependencies.
3. Update any dependencies with known critical vulnerabilities.
4. Update any dependencies that are more than 6 months behind.
5. Document any dependencies that are intentionally pinned.

**Acceptance:**
- No critical vulnerabilities in any dependency.
- All dependencies are within 6 months of their latest release (or documented
  as intentionally pinned).
- The quality gate still passes after updates.

**Dependencies:** None.

## 3. Stream C — Features (New Capabilities)

These are new features that expand June's capabilities. They are ordered by
impact and dependency.

### C.1 Memory Graph Visualization

**Problem:** The graph nodes/edges exist in SQLite but the UI shows a flat list.
A force-directed graph view would make the memory system tangible and help users
understand what June knows about them.

**Fix:** Build a graph visualization component:
1. Add a `/memory/graph` API endpoint that returns nodes and edges in a format
   suitable for D3.js or a similar library.
2. Build a Svelte component that renders the graph as a force-directed layout.
3. Allow clicking on a node to see its details and related facts.
4. Allow filtering by node type (person, place, concept, etc.).

**Acceptance:**
- The graph renders with >100 nodes without janking.
- Clicking a node shows its details in a side panel.
- The component is responsive (works on mobile).
- 5 new tests covering: API endpoint, node filtering, edge rendering.

**Dependencies:** None.

---

### C.2 Skill Plugin System

**Problem:** Skills are MCP servers with a manifest, but there is no lifecycle
hook system. Skills cannot integrate deeply with June's runtime (e.g., run
on startup, react to messages, modify context).

**Fix:** Add a plugin system with lifecycle hooks:
1. Define hooks: `on_startup`, `on_message`, `on_shutdown`, `on_tool_call`.
2. Skills declare which hooks they implement in their manifest.
3. The loop calls registered hooks at the appropriate points.
4. Hooks are gated by the guard layer (a hook cannot bypass security).

**Acceptance:**
- A skill can register for `on_startup` and run code when June starts.
- A skill can register for `on_message` and see (but not modify) incoming messages.
- A skill cannot bypass the guard layer through hooks.
- 10 new tests covering: hook registration, hook invocation, hook gating.

**Dependencies:** None.

---

### C.3 Voice Input/Output

**Problem:** Voice is deferred in the v0.3 plan. If launched with voice, June
becomes a genuinely different product from a chat window.

**Fix:** Add voice capabilities:
1. **Input:** Use the Web Speech API (browser) or a local Whisper model
   (desktop) for speech-to-text.
2. **Input:** Use the Web Speech API (browser) or a local TTS model (desktop)
   for text-to-speech.
3. Add a microphone button to the composer.
4. Add a speaker button to message bubbles.
5. Add a "voice mode" toggle in settings.

**Acceptance:**
- Speech-to-text works in the browser (Web Speech API).
- Text-to-speech works in the browser (Web Speech API).
- The desktop app uses local models for both (no cloud dependency).
- Voice mode is toggleable in settings.
- 10 new tests covering: STT, TTS, mode toggle.

**Dependencies:** None, but large scope. Consider deferring to v0.5.

---

### C.4 Night Shift Mode

**Problem:** Night Shift is deferred in the v0.3 plan. It must be auditable
and reversible before it touches memory.

**Fix:** Build an auditable consolidation system:
1. At a user-configured time (default: midnight), June reviews the day's
   conversations and memory writes.
2. June consolidates redundant facts, resolves contradictions, and
   updates validity windows.
3. Every consolidation action is logged to the Trust Ledger.
4. The user can review and undo any consolidation.

**Acceptance:**
- Consolidation runs at the configured time.
- Every consolidation action is in the Trust Ledger.
- The user can undo any consolidation from the UI.
- 15 new tests covering: consolidation, logging, undo.

**Dependencies:** Phase 11 (memory provenance and quarantine) is a prerequisite.

---

### C.5 Location Awareness (Phase 9)

**Problem:** June cannot locate the user in the world. No timezone, locale,
units, or weather.

**Fix:** Implement the four constraints from the v0.3 plan:
1. **ADR 0032:** OS geolocation, asked once at point of use.
2. **Tauri location permission:** Requested when the user asks for something
   that needs place.
3. **Place block:** City, region, timezone, locale, units — read-time, no timer.
4. **Weather:** First-class read through the existing gated egress path.

**Acceptance:**
- June asks for location once, at point of use.
- Location is coarsened to city level before storage.
- Location is visible, editable, and deletable in `/settings`.
- Weather is surfaced in Receipts like any other network read.
- 20 new tests covering: permission flow, coarsening, storage, weather.

**Dependencies:** None, but large scope.

---

### C.6 Export/Import of Full June State

**Problem:** Migration between machines or backup is not surfaced as a
user-facing feature. The import/export code exists in memory but is not
accessible.

**Fix:** Build an export/import UI:
1. Add a `/settings/export` page that exports the full `june.db` as a
   downloadable file.
2. Add a `/settings/import` page that imports a `june.db` file.
3. Validate the imported file (check schema version, integrity).
4. Show a preview of what will be imported (fact count, entity count, etc.).

**Acceptance:**
- Export produces a valid `june.db` file.
- Import restores the database and all data.
- Import validates the file and shows a preview.
- 10 new tests covering: export, import, validation, preview.

**Dependencies:** None.

## 5. Standing Rules

- Graceful degradation ships in the same change as any model-judgment feature.
- Every privacy-boundary change is documented in the commit that makes it.
- ADR before implementation for anything touching the boundary or the stores.
- `./tools/check.sh` green before every push, read directly, never through a pipe.
- June is "June" or "it", never "she"; "no account needed", not "no account".
- Accessibility and Playwright coverage extend with each surface, not in a sprint
  at the end.
- A published number is a promise. If a benchmark regresses, the number changes
  in the same commit as the code.
