# June v0.4 — Development Plan

**Created:** 2026-07-28. **Amended:** 2026-08-18 (Stream D added).
**Status:** Active. Stream A landed; Stream D is the current work.

This plan builds on the v0.3 launch work (Phases 0-7) and addresses the
identified defects, upgrades, and new features. It is organized into four
streams: **Fixes** (immediate, high-impact), **Upgrades** (infrastructure and
coverage), **Features** (new capabilities), and **Correctness and coherence**
(the 2026-08-18 audit).

Stream D is where the work is. It comes from a line-by-line audit that found
three defects on the live chat path and one structural problem larger than all
of them: the v1 product was never deleted, and it still owns most of the tool
surface the model sees. Stream D is sequenced so each slice is independently
landable and the branch is pushable at every step.

For the authoritative state of what is shipped, see [`../CURRENT.md`](../CURRENT.md).
For the durable worldview, see [`../vision.md`](../vision.md).

## 1. Stream A — Fixes (Immediate) — LANDED 2026-07/08

These are small, high-impact changes that address published defects or
inconsistencies. Each is a single slice: one piece of work → `./tools/check.sh`
green → one commit → push.

### A.1 Temporal Signal Ranking

**Problem:** ADR 0024 claims four recall signals (vector, BM25, entity, temporal)
but the temporal signal does not change ranking when ablated. The `_temporal_prior`
function in `recall.py` applies only to `valid_to`-based expiry, not to recency
of the fact itself.

**Root cause:** The temporal signal is a filter (exclude expired facts), not a
ranker (prefer recent facts). The salience score already includes a recency
component, but it operates on `last_accessed` (when June saw the fact), not on
`valid_to` (when the fact stopped being true in the world). These are different
signals and both matter.

**Fix:** Add a `valid_from` recency prior to the fusion score. Facts with a
recent `valid_from` get a small boost; facts with no `valid_from` are treated as
always-valid (current behavior). This makes the temporal signal contribute to
ranking, not just filtering.

**Acceptance:**
- Ablating the temporal signal changes recall@8 by ≥2% on the golden corpus.
- ADR 0024 is amended to describe the four signals accurately.
- 202ms p95 latency is unaffected (the signal is a multiplicative prior, not a scan).

**Dependencies:** None.

---

### A.2 `distractor_heavy` Recall Improvement

**Problem:** Recall@8 on `distractor_heavy` queries is 0.31, the weakest category.
This shape is most like real-world failure: the user asks about something specific
and the system must distinguish it from similar-but-wrong facts.

**Root cause:** The candidate pool (20) is too wide for this query shape. Wide
pools feed RRF more noise, and distractor-heavy queries are exactly where noise
hurts. The BM25 channel also underperforms on these queries because the
distractors share vocabulary with the target.

**Fix:** Two changes:
1. Reduce the default candidate pool from 20 to 15. Measured: recall@8 rises
   from 0.760 to 0.790 on the full corpus at this setting. The 20-pool was
   chosen for margin against overfitting, but 15 still has margin (the corpus
   best was 12).
2. Add a BM25 term-frequency penalty: facts that match many query terms but
   not the rarest term get a small score reduction. This penalizes distractors
   that share vocabulary with the target without penalizing the target itself.

**Acceptance:**
- `distractor_heavy` recall@8 improves from 0.31 to ≥0.45.
- Full corpus recall@8 does not regress (must stay ≥0.760).
- p95 latency stays under 250ms (ideally improves with a smaller pool).

**Dependencies:** None.

---

### A.3 Retrieval Latency Optimization

**Problem:** p95 retrieval is 252ms at 50k facts, missing the 120ms target.
The vec0 scan is brute-force and grows linearly.

**Root cause:** sqlite-vec's `vec0` index performs a full cosine similarity scan
over all vectors. At 50k facts, this is measurable. The FTS5 channel is fast
(BM25 is index-native), but the vector channel dominates latency.

**Fix:** Three-pronged approach:
1. **Reduce candidate pool** (from A.2): fewer vectors to scan means less work.
   Measured: p95 drops from 252ms to ~210ms with pool=15.
2. **Add a pre-filter:** Before the vector scan, filter `semantic_facts` by
   `valid_to IS NULL OR valid_to > now` in SQL, then only scan vectors for
   currently-valid facts. This reduces the index size proportionally to the
   number of expired facts.
3. **Explore HNSW:** sqlite-vec supports HNSW indices (`vec0` vs `hnsw`). A
   benchmark spike comparing the two at 50k facts. If HNSW improves p95 by
   ≥50%, adopt it; if not, document why and move on.

**Acceptance:**
- p95 retrieval at 50k facts is under 150ms (revised target; 120ms may require
  HNSW or a different index).
- Recall@8 does not regress from any optimization.
- ADR 0024 is updated with the measured latency and the optimization applied.

**Dependencies:** A.2 (smaller pool).

### A.4 Promise Checkpoint/Resume

**Problem:** Resuming a promise re-runs the goal from scratch. This undercuts
the "continues, not completes" inversion (ADR 0015). A promise that was
half-done and got interrupted starts over, wasting the work already done.

**Root cause:** `TaskRuntime._stream_events` creates a fresh `SessionState`
with an empty message list. There is no mechanism to inject the prior steps'
results as context for the resume.

**Fix:** Add a checkpoint mechanism:
1. When a promise is interrupted (cancelled, failed, or blocked), persist the
   accumulated `TaskStep` entries as a checkpoint.
2. On resume, inject the checkpoint as context: "You previously completed these
   steps: [summary]. Continue from where you left off."
3. The loop sees this as a new user message containing the checkpoint summary,
   so it can skip already-completed work.

**Acceptance:**
- A promise that completed 3 of 5 steps before interruption resumes and
  starts from step 4 (not step 1).
- The checkpoint summary is visible in the task's trace.
- Non-idempotent steps (e.g., a tool call that sends a message) are not
  re-executed on resume.
- 15 new tests covering: checkpoint creation, checkpoint injection, partial
  resume, full resume, idempotency tracking.

**Dependencies:** None.

### A.5 Telegram Skill Consumer

**Problem:** The Telegram skill writes to `skill_inbound_events` but nothing

**Decision: Build the consumer** (approved 2026-07-28).

- Estimated scope: Medium (new module, tests, API route for status).

**Dependencies:** None.

### C.2 Skill Plugin System

**Problem:** Skills are MCP servers with a manifest, but there is no lifecycle
hook system. Skills cannot integrate deeply with June's runtime (e.g., run
on startup, react to messages, modify context).

**Fix:** Add a plugin system with lifecycle hooks:
1. Define hooks: `on_startup`, `on_message`, `on_shutdown`, `on_tool_call`.
2. Skills declare which hooks they implement in their manifest.
3. The loop calls registered hooks at the appropriate points.
4. Hooks are gated by the guard layer (a hook cannot bypass security).

**Acceptance:**
- A skill can register for `on_startup` and run code when June starts.
- A skill can register for `on_message` and see (but not modify) incoming messages.
- A skill cannot bypass the guard layer through hooks.
- 10 new tests covering: hook registration, hook invocation, hook gating.

**Dependencies:** None.

### C.4 Night Shift Mode

**Problem:** Night Shift is deferred in the v0.3 plan. It must be auditable

4. The user can review and undo any consolidation.

**Acceptance:**

**Dependencies:** Phase 11 (memory provenance and quarantine) is a prerequisite.

## 4. Stream D — Correctness and coherence (2026-08-18 audit)

Source: a line-by-line audit of `main @ 78885078`. Three defects sit on the live
chat path and are proven by failing tests; one structural problem is larger than
all of them. Full write-up and evidence in
[`repo-audit-2026-08-18.md`](repo-audit-2026-08-18.md).

The stream is ordered **general to specific**: each slice fixes the rule before
it fixes the instances. D.2 and D.3 both exist because a single invariant was
implemented more than once and drifted in the copy nobody re-read; the fix is one
implementation plus a test that fails when a second one appears.

Every slice is independently landable: one slice → `./tools/check.sh` green →
one commit → push. A slice that spans sessions records its stopping point in its
own **Status** line.

### D.1 Direction of record

**Problem:** The documents describe a product the tool surface no longer matches,
and three of them state invariants that the code does not keep. `CLAUDE.md` says
memory sits behind one `MemoryManager` (18 modules bypass it); the "do NOT
reintroduce" list reads as a guard against reintroduction when the v1 product was
in fact never removed.

**Fix:** Amend `CLAUDE.md`, `docs/CURRENT.md`, `ROADMAP.md` and this plan so the
written direction matches both what is true now and what Stream D changes. State
the v1 deletion as an explicit goal rather than an implied one.

**Acceptance:**
- No document asserts an invariant that a Stream D slice is about to falsify.
- `CLAUDE.md` describes the store as one connection factory, not one manager.
- The audit is linked from `CURRENT.md` as the reason for Stream D.

**Dependencies:** None. **Status:** Done 2026-08-18.

### D.2 One privacy predicate, failing closed

**Problem:** Three modules implement "is the user in Local-only mode."
`updates.py` returns `True` when the dial read raises, with the comment "a config
failure must not open the gate." `providers/provenance.py` and
`loop/handwritten.py` return `False` — cloud calls and networked tools proceed.
The correct answer is already in the repo; it exists in three copies and drifted
in two.

No natural path that makes `get_privacy_dial()` raise was demonstrated —
`load_stored_config()` and `load_secret()` are both guarded internally. This is
defense-in-depth on the product's central claim, not a live hole.

**Fix:** A single `june_brain/privacy.py` exporting `egress_permitted()`, which
returns `False` on any exception. Delete the three local copies. Add a gate check
that `get_privacy_dial` is imported only by `privacy.py` and the settings routes.

**Acceptance:**
- Patching the dial read to raise blocks egress at every call site.
- The `updates.py` behaviour is unchanged (it was already correct).
- `check.sh` fails if a fourth copy of the predicate appears.

**Dependencies:** None. **Status:** Done 2026-08-18. Landed
`june_brain/privacy.py` (`local_only` / `egress_permitted` / `dial_value`), a
`check.sh` caller restriction, and `test_invariants.py`. One behaviour change:
`test_provenance_gate.py::test_import_error_falls_back_to_not_local_only` had
pinned the fail-open as intended graceful degradation; it now asserts the call
is refused, and is renamed accordingly.

### D.3 One question about what reaches the network

**Problem:** `guard/actions.py` owns classification and gets it right:
`classify_action()` derives `write_network` from a prefix table (`send_`, `post_`,
`publish_`, `email_`, `notify_`, `sms_`, `tweet_`), and `NETWORK_TOOLS` holds the
three *read*-network tools. But `loop/wiring.is_network_tool()` tests membership
in `NETWORK_TOOLS` instead of asking the classifier, so it answers "is this one
of three named read tools" when it means "does this reach the network."

`is_network_tool` drives two things: the Local-only partition in `stream_turn` —
which grep confirms is the only local-only gate for tools anywhere in the loop,
guard or dispatch layers — and `provenance.egress`. So every outbound write is
both unblocked under Local-only and absent from the provenance frame. The guard's
own module docstring names `write_network` as the primary exfiltration vector.

Nothing shipped currently trips this: the only `send_` tool is in the Telegram
skill, which is `enabled=False` and needs a bot token. It goes live the moment
that skill is switched on.

**Fix:** `is_network_tool` delegates to `classify_action`. The class stays
name-derived, so the threat model's reasoning in §2.1 is undisturbed and the
ledger stays honest about what a call *is*.

**Acceptance:**
- A test asserts the loop and the guard agree across read, write and local probes.
- Local-only blocks a `write_network` call and the trace shows it blocked.
- `provenance.egress` lists a `write_network` call that ran.

**Dependencies:** None. **Status:** Done 2026-08-18. `is_network_tool()` now
returns `classify_action(name) in {read_network, write_network}`; the
`NETWORK_TOOLS` re-export is gone from `loop/wiring.py`. Two tests in
`test_invariants.py` pin it — one comparing the two functions across read, write
and local probes, one asserting the write direction on its own so a partial
revert cannot pass.

### D.4 One engine

**Problem:** ADR 0018 says the hand-written loop is the one engine and the live
chat path. There are two entry points that have become two engines.

`Provider.stream()` yields `str`, so it structurally cannot carry a tool call.
`GemmaProvider.stream()` sends `tools=` to the model and then reads only
`delta.content`; `delta.tool_calls` is never touched. `run_turn` resolves native
calls first via `_resolve_tool_calls`; `stream_turn` builds a text-only
`pseudo_result` and calls `_extract_tool_calls`. Every production caller — the
chat route, the promise runtime, the Telegram consumer — uses `stream_turn`.
`run_turn` is reached only by `loop/experiment.py` and `tools/reliability_harness.py`.

Consequence: a model that answers with a native tool call produces no content
deltas, so the tool never runs and the user receives an empty reply. Proven by
test. The same divergence means the reliability baseline in
`docs/experiments/` measures an engine no user reaches.

**Fix, in two slices so the user-visible bug closes first:**

- **D.4a** — stop passing `tools=` in `stream()`. Removes the blank-reply failure
  immediately at the cost of admitting native calling is off on the live path.
- **D.4b** — widen the stream seam: `stream()` yields a typed `StreamDelta`
  (text | reasoning | tool_calls), both providers assemble streamed tool-call
  fragments, and `stream_turn` prefers native calls over prose extraction.
- **D.4c** — make `run_turn` a drain of `stream_turn` rather than deleting it,
  so non-streaming callers keep their ergonomics and there is one
  implementation of a turn. `loop/experiment.py` and
  `tools/reliability_harness.py` then measure the live path with no change of
  their own. Re-run the baseline.

**Acceptance:**
- D.4a: a provider that emits only a native tool call no longer yields an empty turn.
- D.4b: the same provider dispatches the tool through `stream_turn`.
- D.4b: `run_turn` no longer exists; no caller references it.
- D.4b: `docs/experiments/` records the re-measured baseline and says which
  engine it describes.

**Dependencies:** sequential. **Status:** D.4a, D.4b and D.4c done 2026-08-18.
Open: re-running the reliability baseline, which needs a live Ollama.

D.4a removed `tools=` from both providers' `stream()` and both `stream_turn`
request sites, closing the blank-reply bug immediately.

D.4b added `StreamDelta` (text / reasoning / tool_calls) to `providers/base.py`
and `_assemble_tool_calls()` for the fragment reassembly streaming requires —
a call arrives as a name in one chunk and argument JSON sliced across the next,
keyed by index, so it is accumulated and emitted once at end of stream. Both
providers advertise tools again and yield typed deltas; `stream_turn` normalises
`StreamDelta | str` and prefers native calls, with prose-JSON still the fallback
(invariant 6). The loop's generate-fallback collects `result.tool_calls` too, so
a stream failure no longer also loses the tool.

The seam accepts a bare `str` as a text delta. That is deliberate, not
transitional: a text-only provider has no reason to construct a model per token,
and it kept 26 test doubles working rather than turning a bug fix into a
26-file rewrite.

`test_stream_turn_dispatches_native_tool_calls` in `test_invariants.py` is the
defect asserted end to end — it fails on any commit before D.4b.

Three tests changed direction twice across D.4a and D.4b, and their docstrings
record why: the invariant ("a seam only advertises what it can carry") never
moved, but D.4a satisfied it by abstinence and D.4b by capability.

D.4c kept `run_turn` as a wrapper instead of deleting it. Deleting it would have
rewritten ~15 test cases that exercise real wiring; draining `stream_turn`
instead moved all of them onto the live path, which is a coverage gain rather
than a cost. Two behaviour differences surfaced and both are the streaming
path's semantics, now inherited:

- **Token counts are estimates.** A streamed response does not reliably carry a
  usage block, so the loop estimates from the rendered prompt and the answer.
  `test_handwritten_local_reply` asserted the provider's exact 12/7; those were
  never the numbers a user's Glass Box frame showed, because nothing in
  production called `generate()` through the loop.
- **The reply is the final iteration's text.** The drain clears accumulated
  tokens on each `prompt` event, which opens an iteration. Clearing on
  `tool_call` instead looks equivalent and is not: it empties the answer when
  the loop exhausts `max_iterations` while still calling tools.

Test doubles whose `stream()` was a stub now delegate to their own `generate()`,
so a double cannot contradict itself.

### D.5 Delete the v1 product

**Problem:** The largest single thing wrong with the repo, and not a defect —
the 2025 life-coach product was never removed. Measured: **30 of the 54 tools in
`JUNE_TOOLS`, spanning 919 of the 1,484 lines of `tools.py`**. Worse, the trimmed
set the default local model receives, `JUNE_TOOLS_GEMMA`, is **24 tools of which
none belong to the current product** — no recall, no promises, no search, no
skills. On the default local path June's entire advertised vocabulary describes a
fitness-and-journaling app while `docs/product/overview.md` describes a trusted
continuity engine.

This is also a live cost, not only an aesthetic one: thirty irrelevant tools in
the prompt is a plausible cause of a small local model picking the wrong one, and
wrong picks are the reason `tool_aliases.py` exists as 391 lines of alias and
parameter normalisation.

Must land before the MCP server work, or the wrong tool surface is exported to
every client that connects.

**Fix, one slice per layer so the gate stays green throughout:**

- **D.5a** — the v1 domain tools in `tools.py`. Split into two tranches after
  the delete list turned out to contain tools the *current* product plausibly
  needs:
  - **tranche 1 (done)** — unambiguous v1: health and fitness (gym, food,
    workouts, body metrics, habits, nutrition, water, recovery readiness,
    progress), mood tracking (the behavioral floor says June is not a
    therapist), chapters (completeness, intake, weekly summary), and
    conversation coaching (compatibility, conversation starters, difficult
    conversations). Plus the five no-op UI tools. 27 tools removed.
  - **tranche 2 (needs a decision — see below)** — preferences, relationships,
    goals, open loops, calendar, journal, favorites.

**The tranche 2 question.** These read as v1 residue by origin but overlap the
current product by function: `save_user_preference` is close to the heart of
"remembers what matters"; `save_open_loop` is a standing intention, which is
inversion 2 under a different name than Promises; calendar is the Time track in
`ROADMAP.md`. Deleting them shrinks the prompt; keeping them means deciding
whether they are the memory-write surface the product actually lacks.

Related finding, which makes this a design question rather than a cleanup one:
**June has no model-callable memory tools at all.** Recall happens automatically
in `ContextAssembler`; Promises are managed through `/tasks`, not by the model.
So "rebuild the local tool set from the real product" cannot be done as written
— the product tools do not exist. After tranche 1, `JUNE_TOOLS_GEMMA` is 11
tools and every one is either a v1 memory-write or a runtime control.

The decision to take: either (a) tranche 2 stays as June's memory-write surface
and is renamed/reframed to match the product, or (b) tranche 2 goes and a small
deliberate set (`remember`, `forget`, `list_promises`, `update_promise`) is
designed to replace it. (b) is the better product; (a) is the cheaper step.
Not to be settled inside a cleanup slice.
- **D.5b** — `context_intelligence.py` (602), the `Memory` domain methods in
  `memory/sqlite.py` (~1,000), and their DAOs.
- **D.5c** — `skills/health` (169), `skills/daily` (141), `routes/demo.py` (167),
  and the API schemas and routes that serve them.

  **`skills/health` and `skills/daily` are done, and had to be**, because
  deleting a native tool does not remove the capability. `_select_tools_for_runtime`
  filters skill tools by `t.name not in native_names`, so a native tool
  *shadows* the skill's copy — and removing the native copy **unshadows** it.
  After tranche 1, `log_mood`, `log_water`, `log_body_metrics`,
  `log_workout_session`, `log_habit_completion` and `get_today_summary` were
  still advertised, now served by the skills instead of natively.

  The gate cannot see this class of problem: `check.sh` exports
  `JUNE_SKILLS_DISABLED=1`, so no test in the suite ever observes the assembled
  tool list with skills loaded. Worth a follow-up — the tool surface the model
  actually receives is currently untested.
- **D.5d** — the tests pinning the above, and a re-measure of tool-selection
  accuracy to decide how much of `tool_aliases.py` still earns its lines.

**Settled 2026-08-18 — the five UI-control tools all go.** `set_ui_focus`,
`set_ui_checklist`, `set_ui_layout`, `set_ui_chapter` and `clear_ui_workspace`
are **no-ops**: each formats a confirmation string and returns it, writing
nothing. Nothing in `apps/web/src`, `packages/ui/src` or `packages/api/src`
references them. They are the residue of a v1 "workspace panel" that no longer
exists.

They are worse than dead weight. `set_ui_focus` tells the model "Workspace focus
updated to X" when no workspace was updated, so a tool result asserts something
untrue and the model relays it to the user in good faith. That is a Glass Box
violation reached without any component behaving incorrectly — every layer is
honest about a lie it was handed. Delete them in D.5a rather than treating them
as UI surface to preserve.

`create_schedule` / `list_schedules` / `delete_schedule` stay — the scheduler is
a supported product feature (ADR 0016, user-requested deterministic jobs).

**Acceptance:**
- `JUNE_TOOLS_GEMMA` contains no v1 domain tool.
- Every remaining tool maps to a capability named in `docs/product/overview.md`.
- The retrieval and reliability benchmarks are re-run and their numbers updated.
- Schema migration: existing rows in dropped tables are exported by
  `memory/export.py` before the tables go, or the tables are left in place and
  only the code is removed. Decide explicitly and write it in the commit.

**Dependencies:** D.4 first (so the engine is settled before the tool surface
moves). **Status:** Not started.

### D.6 Proactivity out of the scheduler

**Problem:** `scheduler/agent.py` states "June never creates them on a timer for
proactive engagement (ADR 0016)" and then calls `build_system_prompt`, which
injects a day-of-year chapter rotation, a daily maintenance question, detected
patterns ("workout gaps", "sustained low energy") and a "JUNE'S SUGGESTION FOR
TODAY" line. A user who asked for an 8am reminder gets a life coach.

Three stated invariants at once: inversion 4 (never on a timer), the behavioral
floor's ban on engagement-maximizing metrics, and its rule that sensitive
memories are surfaced by the user rather than volunteered.

Scope, stated fairly: this is the scheduler path only. The live chat path uses
`ContextAssembler` and never touches it.

**Fix:** Delete `patterns.py` (295) and the `daily_focus`, `patterns_context` and
`suggestion_context` blocks from `build_system_prompt`. A scheduled job gets the
same system prompt as any other turn plus the user's own instruction. Delete
`test_patterns.py` and `test_daily_suggestion.py` — they currently keep abandoned
behaviour green and looking maintained.

**Acceptance:** A scheduled job's assembled prompt contains no content the user
did not ask for. **Dependencies:** D.5 (shares the domain deletion).
**Status:** Done 2026-08-18, and it became urgent rather than optional:
`_BASE_INSTRUCTIONS` still instructed the model to call tools that tranche 1 had
deleted, so a scheduled job's prompt was advertising a toolbox that no longer
existed.

Removed: `patterns.py` and its two test files, `_DAILY_CHAPTER_ROTATION`,
`_DAILY_MAINTENANCE_QUESTIONS`, and the `daily_focus` / `patterns_context` /
`suggestion_context` blocks.

`_BASE_INSTRUCTIONS` was rewritten rather than trimmed. It had opened with a
13-chapter inventory (Gym Schedule, Food Schedule, Habits, Body Metrics, Water),
an AUTOMATIC CAPTURE section headed "do this every single turn without being
asked", a PROACTIVE DATA GATHERING section instructing June to interrogate the
user about empty chapters in priority order, and a DAILY TRACKING BEHAVIOUR
section beginning "Every day, ask at least one question". That is three of the
four inversions contradicted in one string. The replacement saves what the user
offers, names only surviving tools, and says explicitly not to volunteer
observations about patterns, health or mood.

### D.7 Exception discipline

**Problem:** 203 `except Exception` handlers in non-test source, ~29 falling
through to a bare `pass`; the harness loop alone has 34. The pattern implements
graceful degradation and is usually right, but it is applied uniformly, and
uniform silence is what produced D.2. Three situations wear one costume: a
decorative feature failing (fine to swallow), a functional feature failing (must
degrade *and* tell the user, per the Glass Box), and a safety check failing (must
fail closed, loudly).

**Fix:** Two helpers, `degrade_quietly()` and `fail_closed()`, so intent is
visible at the call site. Any handler guarding a privacy, guard, ledger or
consent decision uses `fail_closed`. Enable ruff `S110` and require a log line.

**Acceptance:** ruff `S110` clean; every safety-adjacent handler uses
`fail_closed`. **Dependencies:** D.2 establishes the pattern.
**Status:** Not started.

### D.8 Papercuts

**Problem:** Small, independently true defects found during the audit.

- Token double-count in `stream_turn`'s generate-fallback: `result.*_tokens` are
  added, then `estimate_tokens(...)` is added for the same content. Every
  fallback turn reports roughly double, and the Glass Box shows the user.
- A ~35-line copy-paste of the tool-call-suppression buffer, once in the stream
  loop and once in the `splitter.flush()` block. The copies have already
  diverged: the flush copy is missing the `continue` for an unterminated fence.
- `_assert_protocol()` at `handwritten.py:841` is documented as running at import
  time and is never called.
- `make_tools_block`'s docstring says the loop "does not bind structured tools
  through the provider API"; `make_tool_specs` twenty lines below does exactly
  that. `check.sh`'s mypy comment cites "LangGraph ToolNode state typing";
  LangGraph was removed in the rebuild.
- `apps/web/src/routes/system/+page.svelte` (1515 lines) and `skills/+page.svelte`
  (1335) were never decomposed into `packages/ui` the way chat was.

**Fix:** One commit each. **Dependencies:** the fence/buffer extraction is
easier after D.4b. **Status:** Done 2026-08-18, except the two fat Svelte admin
pages, which stay open.

The token double-count is fixed by preferring the provider's reported usage when
the generate-fallback ran, instead of adding an estimate of the same turn on top.
Pinned by `test_generate_fallback_does_not_double_count_tokens`.

The duplicated suppression buffer became `_AnswerGate`. The two copies were not
identical by nature and should not have been collapsed blindly: mid-stream an
unterminated ``` fence means "wait for more deltas", and at end-of-stream there
are none, so the text must be released rather than dropped. That is now the
`final` flag — the difference is deliberate and documented instead of a drift
between two copies where one had simply lost a `continue`.

`_assert_protocol()` is gone; `test_loop.py:92` already asserts the
`runtime_checkable` conformance it claimed to provide. The `make_tools_block`
and `check.sh` docstrings now describe what the code does.

### D.9 Invariants become gate checks

**Problem:** `CLAUDE.md` lists seven invariants and none are enforced by anything
but attention. Every finding in the top band of the audit has the same shape: a
rule written once in a document, implemented more than once in code, drifted in
the copy nobody re-read.

**Fix:** `packages/brain/tests/unit_tests/test_invariants.py` holds one test per
invariant, landing with the slice that makes it pass. Where a test cannot express
the rule, `check.sh` gets a grep — as with the `get_privacy_dial` import
restriction in D.2.

**Acceptance:** Each of the seven invariants in `CLAUDE.md` names the test or gate
check that enforces it, or is rewritten to stop claiming enforcement it does not
have. **Dependencies:** accumulates across D.2–D.7. **Status:** In progress.

## 5. Phase Ordering

Stream D displaces the remaining pre-launch items. Announcing a product whose
pitch is "the agent that can prove what it did" while the live chat path can drop
a tool call, and while Local-only does not stop an outbound write, would invert
the pitch at the moment of maximum scrutiny — the same reasoning that gated
Phase 7 on SSRF and the packaged binary.

### Landed
- **A.1–A.5** — retrieval, latency, promise checkpoint, Telegram consumer
- **B.2** — e2e spec for `/setup`
- **D.1** — direction of record

### Now (before launch)
1. **D.2** — one privacy predicate, failing closed
2. **D.3** — one question about what reaches the network
3. **D.4a** — stop advertising tools on a seam that cannot carry them
4. **D.4b** — typed stream delta; retire the second engine
5. **D.5** — delete the v1 product (a–d, one slice per layer)
6. **D.6** — proactivity out of the scheduler
7. **B.1** — git history rewrite (must be done before anyone forks)

### Post-launch (first iteration)
8. **D.7** — exception discipline
9. **D.8** — papercuts
10. **B.3** — e2e specs for other routes
11. **B.5** — dependency audit
12. **C.1** — memory graph visualization (high UX impact)

### Later (v0.5+)
13. **B.4** — Linux platform support
14. **C.2** — skill plugin system

16. **C.4** — Night Shift mode

**D.9 runs alongside, not in sequence:** each slice above lands its invariant
test with it.

## 6. Standing Rules

- Graceful degradation ships in the same change as any model-judgment feature.
- Every privacy-boundary change is documented in the commit that makes it.
- ADR before implementation for anything touching the boundary or the stores.
- `./tools/check.sh` green before every push, read directly, never through a pipe.
- June is "June" or "it", never "she"; "no account needed", not "no account".
- Accessibility and Playwright coverage extend with each surface, not in a sprint
  at the end.
- A published number is a promise. If a benchmark regresses, the number changes
  in the same commit as the code.
