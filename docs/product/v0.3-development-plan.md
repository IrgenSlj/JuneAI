# June v0.3 — Development Plan

**Created:** 2026-07-24. **Consolidated:** 2026-07-27.
**Status:** Active. The single plan of record.

This is the only plan document. It holds the *what*, the *why*, and the *order*,
because keeping those in separate files produced two docs that disagreed within
a day of each other. Where any other doc conflicts with this one, this one wins
and that one should be archived.

For the authoritative state of what is shipped, see [`../CURRENT.md`](../CURRENT.md).
For the durable worldview, see [`../vision.md`](../vision.md).

Every slice is: one piece of work → `./tools/check.sh` green → one commit →
push. No batching.

**No day estimates.** Earlier versions carried them; the work has repeatedly
discovered its own scope mid-slice and nobody tracked against them. They
conveyed precision that did not exist. Slices are sized to be finishable in a
sitting; that is the only estimate that has held.

## 2. Competitive position

**Updated 2026-07-27** with the Snyk ToxicSkills audit, which changes the shape
of the argument.

| Competitor | Their strength | Their weakness |
|---|---|---|
| **OpenClaw** | ~355K GitHub stars in five months, millions of users, huge plugin ecosystem, self-hosted, 24 messaging channels | 40,214 internet-exposed instances, 35.4% flagged vulnerable (SecurityScorecard, Feb 2026); CVE-2026-25253 (Critical, 8.8) one-click host takeover via cross-site WebSocket hijacking; an independent study found 93.4% of verified-vulnerable instances had authentication bypass |
| **The agent-skills ecosystem** | ClawHub + skills.sh: thousands of installable capabilities | Snyk's ToxicSkills audit (3,984 skills, 5 Feb 2026): **36% contain prompt-injection techniques**, 13.4% have critical flaws, **76 confirmed malicious payloads**, **1,467 skills carrying active payloads** targeting OpenClaw, Claude Code and Cursor. **100% of confirmed malicious skills combined a code payload with prompt injection.** Snyk showed three lines of markdown in a `SKILL.md` instructing an agent to read SSH keys and exfiltrate them |
| **OpenMemory (Mem0)** | Local-first MCP memory server, works with Claude Desktop / Cursor / VS Code today | Memory only — no character, no proactivity, no audit trail |
| **Mem.ai, Personal.ai** | Compounding memory | Cloud-only; Personal.ai is $40/mo |
| **Apple Intelligence** | On-device | Ecosystem lock-in, shallow memory |
| **ChatGPT / Claude** | Best general intelligence | No persistent memory, no proactivity |

### What this means

June is **not** differentiated by being local-first and open-source. That race
has a winner with millions of users, and competing there is competing on their
strength.

The live, quantified, *unsolved* problem in this market is the **agent skills
supply chain**. A third of installable capabilities carry prompt injection, and
the documented attacks arrive as **natural-language instructions in markdown**,
not only as code. That is precisely the layer June was built to defend:

- Every tool result enters context inside an untrusted-content envelope.
- A measured injection heuristic scans it, and a detection **revokes standing
  approvals** — an "always allow" stops covering a tool once poison lands.
- Skills declare a capability contract that is **enforced at dispatch**, so a
  skill cannot use a capability it never declared, and approving a tool does not
  approve a skill to exceed its contract.
- Taint is tracked across calls; consequential actions are gated.
- All of it lands in a hash-chained ledger a third party can verify without
  running June.

**Positioning:** *"The agent that can prove what it did"* — sharpened for launch
to lead with the skills-supply-chain angle, because that is where the market
currently hurts and where June's evidence is strongest.

Two honesty constraints on that message, both already in the threat model:
June's contracts limit what a skill can do **through June**, and a fully hostile
skill binary acts without June invoking anything. What June defends is the
**dominant documented vector** — instructions smuggled through content — not
supply-chain trust itself.

### The uncomfortable number

835 commits over 16 months have produced **0 stars, 0 forks, 0 downloads**. The
constraint has never been engineering quality. It is that nobody has been given a
reason or a route to try June. Everything below is ordered by that fact.

### What "launch worked" means

Stated in advance, because a launch with no success criterion cannot fail and
therefore teaches nothing.

| Signal | Floor | Read |
|---|---|---|
| GitHub stars, 7 days | 100 | The pitch is legible to strangers |
| DMG downloads, 7 days | 50 | People will install an unnotarized alpha |
| MCP quickstarts completed | 10 | The zero-install path works |
| Substantive security replies | 3 | The evidence is credible to people who audit |

**If the floor is missed:** the problem is the message, not the engineering. The
response is to rewrite the message and post again to a different audience — not
to build another feature. That rule exists to stop a bad launch from being
answered with six more weeks of code.

## 6. Phase 9 — Orient June in the user's world

June knows *when* it is and whether the user is present. It has no idea *where*
they are. That gap costs more than it looks: no timezone when the user travels,
no local weather, no units, no "the shop closes in an hour."

**Decided 2026-07-27: OS geolocation, asked once.** June asks macOS for the
user's location rather than making them type a city.

That is the more useful answer and it is the founder's call. It is also the
option that costs the most to get right, because a permission prompt on a
privacy-positioned product is a claim being tested. Four constraints make it
defensible, and they are acceptance criteria, not aspirations:

- **Asked at the point of use, never on first run.** The prompt appears when the
  user asks for something that needs place, with June saying what it is for.
  A permission dialog during onboarding, before any value has been delivered, is
  how apps train people to click through prompts.
- **Coarsened before storage.** June keeps city-level precision. Nothing needs
  the metres that CoreLocation returns, and storing them creates a liability with
  no matching benefit.
- **Visible, editable, deletable** in `/settings`, alongside everything else the
  user can see about themselves. Refusing or revoking degrades gracefully to a
  typed city, and then to no place at all.
- **Any egress carrying location is ledgered** like every other network call, so
  "where am I" is answerable from the receipts.

| Slice | Work | Acceptance |
|---|---|---|
| **9.1** | ADR 0031: OS geolocation, the four constraints above, and what happens on refusal | Accepted before code |
| **9.2** | Tauri location permission, requested at point of use, coarsened to city level | Refusal is a supported state, not an error path; a typed city is the fallback |
| **9.3** | Place block alongside the temporal block — city, region, timezone, locale, units — read-time, no timer | Rendered in the assembler; absent entirely when no place is known |
| **9.4** | True timezone handling: store the user's zone, stop inferring it from the machine clock | A user who travels gets correct local time and a correct "tomorrow" |
| **9.5** | Weather as a first-class read, through the existing gated egress path | Surfaced in Receipts like any other network read; blocked in local-only |

## 9. Open questions

These need a decision from the founder. They are listed here rather than left in
a chat log so the next session starts from them.

1. **Location and weather — how far?** Nothing at all / a city the user types
   once and can delete / OS geolocation. This sets the ADR in 9.1 and is a
   privacy-boundary decision, not a technical one.
2. **Launch channel and timing.** Show HN, r/LocalLLaMA, Lobsters — which, in
   what order, and does it wait for the Phase 7 blockers or go with a caveat?
3. **`.git` history rewrite.** 240MB carrying a v1 virtualenv, a 68MB
   checkpoint, and MNIST. Zero forks, so the blast radius is one machine.
   Rewrite before launch, or leave it?
4. **Second platform: Linux or Intel Mac?** Linux is where the competition's
   self-hosters are; Intel Mac is the smaller diff.
5. **Apple Developer account (~$99/yr) for notarization?** Without it every user
   bypasses Gatekeeper to install, which is a bad habit to teach on a security
   product.
6. **Is monetization in scope for v0.3?** There is a licensing module and an
   entitlement route with tiers, wired to no purchase flow. Finish it, or park
   it explicitly?
7. **Brave Search API key.** Ship a shared key, require the user's own, or stay
   on the DuckDuckGo fallback?
8. **Repo workflow permissions.** `default_workflow_permissions` is `read`, so
   CI cannot upload release assets — the `v0.1.0` asset was uploaded by hand.
   Set it to `write`?

## 10. Standing rules

- **Graceful degradation ships in the same change** as any model-judgment feature.
- **Every privacy-boundary change is documented in the commit that makes it.**
- **ADR before implementation** for anything touching the boundary or the stores.
- `./tools/check.sh` green before every push, read directly, never through a pipe.
- **June is "June" or "it", never "she"**; "no account needed", not "no account".
  Gated by `tools/check_doc_hygiene.py`.
- Accessibility and Playwright coverage extend with each surface, not in a sprint
  at the end.
- **A published number is a promise.** If a benchmark regresses, the number
  changes in the same commit as the code.
